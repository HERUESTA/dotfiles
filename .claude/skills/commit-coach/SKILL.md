ユーザーが自分で書いた下書き（$ARGUMENTS）を**添削**して、コミットまで行う。目的はユーザーがコミットメッセージを書く力を伸ばすこと。下書きの意図（特に「なぜ」）はユーザーのものとして残し、AI は形式と言葉を整える。

## Steps

1. **下書きを受け取る**
   - $ARGUMENTS が空なら、メッセージ案を出さずに「まず自分の言葉で1行書いてみてください（雑でOK、なぜ変えたかを入れると◎）」と促して終える。

2. **コミット範囲を決める**
   - `git status` と `git diff --staged` / `git diff` で変更を確認する。
   - ステージ済みの変更があれば、それをコミット範囲とする。
   - 何もステージされていなければ、下書きの内容に関係するファイルを選び、ファイル一覧を示して確認を取ってから `git add` する。
   - 下書きと関係ない変更が混ざっていたら、それを指摘し、分けてコミットすることを勧める。完了条件: コミットするファイルがユーザーと合意できている。

3. **形式を決める**
   - 形式: `<絵文字> <type>: <件名>`（例: `🔧 chore: toggleterm.nvimを導入する`）
   - 下の「gitmoji 採用セット」から、まず type、次にその type の絵文字を選ぶ。迷ったら type の既定（各行の先頭）を使う。
   - 件名は日本語で、**結果**の形（「〜する」「〜を追加」）で書く。
   - 下書きに絵文字や type があれば、差分と合っているかを確かめて添削ポイントに含める。

4. **添削する**
   - 差分と照らして、下書きの事実誤り・抜け・曖昧さを直す。
   - 下書きに「なぜ」があれば、件名か本文に必ず残す。差分から読み取れない理由を AI が作り足すことはせず、必要なら本文に書くかユーザーに尋ねる。
   - 次の形で提示する:

     ```
     下書き: <ユーザーの下書き>
     添削後: <整えたメッセージ>

     添削ポイント:
     - <何をなぜ変えたか（1〜3点）>
     - 良かった点: <下書きで良かったところ（1点）>
     ```

5. **コミットする**
   - 「この内容でコミットしますか？」と確認し、ユーザーが修正を返したら手順4に戻る。
   - 承認されたら HEREDOC で `git commit` し、`git log --oneline -1` で結果を表示する。push はユーザーが頼んだときだけ行う。

## gitmoji 採用セット

[gitmoji](https://gitmoji.dev/) から採用した絵文字。絵文字は gitmoji.dev の表記どおり（`⚡️` `🚑️` などの異体字セレクタ付き）に書く。

| type | 絵文字 | 使うとき | 例 |
|---|---|---|---|
| feat | ✨ | 新しい機能・できることを追加する | プラグイン導入でキー操作が増える、新しいskillやスクリプトを追加 |
| | 🎉 | プロジェクトを始める（最初のコミット） | リポジトリの初期化 |
| fix | 🐛 | 動作の不具合を直す | 起動時のエラー、キーマップが効かない |
| | 🚑️ | 本番などで急ぎ直す必要がある修正 | 今すぐ直さないと作業できない設定の破損 |
| | 🩹 | 不具合ではない小さな手直し | 表示崩れの微調整、オプション値の小修正 |
| | ✏️ | typo を直す | コメントや文言の誤字 |
| docs | 📝 | README・説明文書を追加・更新する | README、plugins.md の追記 |
| | 💡 | ソースコード内のコメントを追加・更新する | 設定ファイルに理由のコメントを足す |
| style | 🎨 | 動作を変えずに構造・書式を整える | インデント、並び順、フォーマッタの適用 |
| | 💄 | UI・見た目を変える | カラースキーム、ステータスラインの見た目 |
| refactor | ♻️ | 動作を変えずに中身を書き直す | 重複をまとめる、関数に切り出す |
| | 🏗️ | 構成・ディレクトリ設計を変える | ファイル配置の整理、モジュールの分割 |
| perf | ⚡️ | 速くする・軽くする | 遅延読み込みにして起動を速くする |
| test | ✅ | テストを追加・更新し、通る状態にする | spec の追加、テストの修正 |
| | 🧪 | まだ失敗するテストを先に追加する（TDDの red） | 再現テストだけを先にコミット |
| build | 📦️ | ビルド成果物・パッケージを変える | ビルド設定、成果物の更新 |
| | ⬆️ | 依存のバージョンを上げる | lazy-lock.json の更新、gem/npm のアップデート |
| | ➕ | 依存を追加する | Gemfile・package.json へのライブラリ追加 |
| | ➖ | 依存を削除する | 使わなくなったライブラリの削除 |
| ci | 👷 | CI の設定を追加・更新する | GitHub Actions のワークフロー追加 |
| | 💚 | 落ちている CI を直す | CI だけ失敗するテスト・設定の修正 |
| chore | 🔧 | 設定ファイルを追加・更新する | dotfiles の設定変更、エイリアス追加 |
| | 🔥 | コード・ファイルを削除する | 不要になった設定やファイルの削除 |
| | ⬆️ | ツールの依存を更新する（アプリ本体の依存でないもの） | 開発ツールのバージョン更新 |
| revert | ⏪️ | 以前のコミットを取り消す | `git revert` のコミット |

迷いやすい組み合わせ:
- **feat と chore 🔧**: 使える操作・機能が増えるなら feat、既存の挙動の設定値を変えるだけなら chore。
- **fix 🐛 と 🩹**: 「壊れていた」なら 🐛、「動くが少し直したい」なら 🩹。
- **style 🎨 と refactor ♻️**: 見た目の書式だけなら 🎨、コードの構造やロジックの書き方まで変えるなら ♻️。
- **build ⬆️ と chore ⬆️**: アプリが実行時に使う依存なら build、開発用ツールの依存なら chore。
